# 商家配送接入说明

本轮范围为商家自行配送至指定校园交接点。保留到摊自取和到摊付款；不包含独立骑手端、自动派单、实时位置、第三方承运接口或送寝服务。配置与订单进度由后端保存，不依赖同一台设备。

当前项目尚未准备真实微信支付主体、商户号和 HTTPS 域名。用户已要求先完成带明确标识的模拟付款与配送体验，可在开发示例环境手动演练完整流程；这不会扣款或安排真实送餐。操作见[模拟体验指南](simulation-guide.md)，本轮结果见[模拟验证记录](simulation-verification.md)。本文的开通顺序针对真实服务，微信接入条件见[支付说明](wechat-payments.md)；此前真实接入代码的测试与限制见[配送验证记录](delivery-verification.md)。

## 开通顺序

1. 运营核实商家交易资格、目标校园允许的交接点、配送人员和异常联系人。在运营后台创建启用的交接点；交接点属于校园区域。
2. 为非示例商户配置自己的独立微信直连商户号，完成真实环境支付、关单、退款和通知联调。示例摊位不发起真实扣款。
3. 运营审核该摊位配送资格。商家可以修改自身配送设置，但不能自行授予审核资格。
4. 商家在店铺设置里选择本区域可用交接点，填写配送费、起送金额、预估时长、每日配送时段、容量，并打开商家配送。
5. 保持出摊和位置确认有效。服务端同时检查交易权限、审核、商家开关、时段、容量、交接点和支付配置；任一条件不满足时暂停新配送订单并给出原因。

配置完成不等于履约能力已验证。真实开放前仍须完成校园安排、包装与运力验证，参见[配送评估](delivery-assessment.md)。

首版使用北京时间的每日一个配送时段，开始时间必须早于结束时间，暂不支持跨午夜或多个时段。容量表示同时进行中的配送订单上限，包含待付款订单，不是当天累计销量。起送金额按餐费计算，不含配送费。预计送达区间从提交订单时计算并保存，仅作预估，不承诺实时分钟必达。

## 学生怎么下单

在单个摊位的结算页选择“商家配送”，选择交接点，填写收餐人和联系电话。页面分别列出餐费、配送费和合计，并展示配送预估与预付规则。配送不提供到摊付款选项；尚未开通支付时仍可选择自取。

提交时，服务端重新核对商品、库存、价格、配送费和服务条件。商品或配送费变化后需要重新确认，不能按页面旧金额扣款。订单保存商品价格、配送费、交接点、联系人及时间预估；商家之后修改配置不会改写历史订单。

配送订单流程为：

```text
待付款 → 待接单 → 制作中 → 待配送 → 配送中 → 已到交接点 → 已完成
```

真实模式只有微信服务端确认付款成功，订单才进入待接单。返回网页、二维码过期或用户点击“已支付”不能作为到账证据。模拟模式由订单本人明确执行模拟付款，状态由后端保存，整单持续标明模拟。两种模式都保留支付不确定时先查询、不能重复付款或改成线下收款的流程。

新配送订单默认保留 15 分钟付款时间。为满足微信创建交易的有效期要求，剩余时间不超过 75 秒时不再创建新的付款入口，应取消后重新下单；已有微信交易继续查询真实结果。服务端核实支付成功后，重新开始接单时限，默认 5 分钟，由运营参数控制；付款等待时间不会消耗商家的接单时限。存在未知支付结果时，超时不直接释放库存或容量，先核对微信交易。

商家标记到达交接点后，学生实际收到餐点再点“确认收餐”；也可以出示订单页的一次性收餐码，由商家核销。商家发出或放到交接点都不会自动完成订单。已完成订单可以评价。

## 商家怎么处理

- 工作台与订单页区分自取、配送。未付款配送单不进入可接单流程；先核实支付，再接单、备餐。
- 出餐后进入待配送。实际送出时点“开始配送”，到达订单约定的交接点后点“已到交接点”。
- 配送人员或商家遇到延误、无法联系、包装问题等，在订单里记录实际异常说明并联系学生。存在未解决异常时不能继续发出、到点或完成收餐；商家处理后填写解决说明再继续，报告和解决均保存操作记录。没有实时轨迹时只显示真实节点。
- 核销收餐码前确认学生已收到餐点。码不能重复使用；商家订单接口不泄露学生收餐码。
- 微信预付不能再点线下收款。退款和付款进度分别展示，商家只能处理所属摊位订单。

## 取消、退款和库存

未付款订单可以取消；若存在微信在途交易，需先核实并关闭交易。支付请求超时、查询暂时找不到交易，并不证明没有扣款，此时保留支付占用等待核对。

已经预付但未接单的配送取消、商家拒单或接单超时，需要保存退款请求并通过原微信交易全额退款，包含配送费。接单后的取消由商家处理；配送进行中有争议时保留订单记录，由商家联系学生处理，不能把页面操作当作已经交付。

微信确认收款时还会核对配送服务条件。若已经超出付款期限、商家暂停或失去接单资格、超出配送时段、原交接点不再获准使用，订单终止并保存全额退款请求；不会给用户悄悄换一个点位。已经关单或终止后又出现矛盾的付款通知则进入人工核对，不恢复原订单。

退款发起、处理中、关闭、异常和成功分别记录。只有微信确认成功才显示已退款；网络重试沿用同一退款号。退款未成功不会恢复已经终止的配送，也不会把款项当作未支付。

未开始备餐的取消或拒单释放一次预留库存；已经备餐的食物不因全额退款自动重新上架。支付、取消、退款、收餐使用服务端状态校验，不能靠前端按钮禁用保证一致性。

## 接口和数据

所有业务接口位于 `/api/v1`，保留登录、CSRF 和订单所有权校验。

| 入口 | 用途 |
| --- | --- |
| 摊位详情的 `delivery` | 当前配送配置、可用交接点、能否接单及原因 |
| `GET/PATCH /merchant/stalls/{id}/delivery` | 所属摊位的配送设置；包含可选点位，审核状态由运营控制 |
| 创建订单的 `fulfillment_type` | `pickup` 为自取；`delivery` 为商家配送 |
| 创建配送订单的 `delivery_point_id`、`recipient_name`、`contact_phone`、`expected_delivery_fee_cents` | 选定点位、必要联系方式与用户已确认的配送费；服务端再次检查 |
| 订单的 `items_total_cents`、`delivery_fee_cents`、`total_cents` | 商品金额、配送费与实际订单总额，单位均为分 |
| 订单的 `delivery_point_*` | 下单时交接点的编号、名称、地址和经纬度快照 |
| 订单的 `recipient_name`、`contact_phone` | 本单收餐联系信息 |
| 订单的 `delivery_eta_min_at/max_at` | 下单保存的预计送达区间，不是真实轨迹预测 |
| 商家动作 `dispatch`、`arrive`、`report_delivery_issue` | 实际送出、到达交接点和异常说明 |
| 商家动作 `resolve_delivery_issue` | 填写解决说明后解除配送异常，保留操作审计 |
| 商家动作 `complete` | 校验学生出示的收餐码后完成 |
| `POST /orders/{id}/confirm-receipt` | 学生在已到交接点后确认自己已收餐 |

支付与退款沿用现有微信接口，金额包括配送费。接口详细字段以服务端序列化器为准；前端不能自行计算一个金额后直接请求支付网关。

## 运行与异常处理

保持 `expire_orders` 与 `reconcile_payments` 任务运行。前者处理订单超时，后者追查在途支付和退款。关闭新的微信支付或配送后，仍需保留处理历史交易所需的收款配置、密钥和查单任务。

自动取消或拒单先把退款请求保存在数据库，即使当时支付配置或网络不可用也不会丢失补偿任务。退款任务使用原编号查询和重试；未付配送超时则先核对并真正关闭微信交易，不能只凭本地时间释放正在付款的订单。

遇到支付未知、迟到支付通知、重复扣款疑似情况或退款异常，运营应核对原订单与微信流水；不能删订单、重置付款状态、释放仍在支付中的库存，或手动把配送标记完成来消除待办。历史交接点保留在订单中，搬摊或换点需联系用户安排，不能静默改地址。

手机同网络访问继续使用当前开发服务的 5183 端口。普通局域网 HTTP 可演练明确标识的模拟支付与配送，但不等于已配置真实微信 H5 支付与 HTTPS 回调。
