# 模拟支付与外卖体验指南

更新日期：2026-09-29。此模式用于先把学生下单、商家接单、配送、取消及退款的操作跑通，**不扣款、不向微信发送请求，也不安排人员实际送餐**。模拟数据保存在后端，刷新页面或用另一设备登录仍可查看。

真实微信 Native/H5 的接口继续保留，切换准备见本文末尾。模拟不等于微信沙箱，不验证微信开户、签名证书、真实网络、到账时间或真实配送能力。实际测试结果单独记录在[模拟验证记录](simulation-verification.md)。

## 商家先做什么

使用示例商家账号进入 `/merchant/store`。页面顶部“经营服务”提供“线上支付”和“外卖配送”开关，修改后自动保存。先确认出摊状态与位置，再开启所需服务。开关是该摊位的服务偏好；模拟开关不会申请微信商户号，也不会改变真实经营资质。

- **线上支付**：打开后，学生可在支持的订单状态使用模拟付款。自取仍在出餐后付款，外卖先模拟付款再交给商家接单。
- **外卖配送**：打开后，“外卖基础设置”直接展示模拟交接点与每单配送费。起送价、配送时段、预计时长和同时进行的单量放在“更多配送设置”里，不需要每次营业重填。
- **位置与营业**：位置过期、收摊、暂歇仍会停止新订单。模拟不会替商家自动开摊、更新位置确认时间或绕过商品库存。

关闭某个服务开关会停止新的相应业务，不会把已存在订单删除或转换为真实订单。处理已有订单时，查看订单自己的模式标记与状态。

2026-09-29 操作补充：

- 配送费、交接点等修改要点“保存配送设置”；页面会显示是否有未保存的修改。其他设备更新设置时，未编辑项自动同步，本机草稿保留；同一项冲突会显示另一设备的新值，核对后再保存。保存只提交本次修改的项。
- 新摊位首次设置位置要填写取餐地址和完整经纬度。首次录入或更换位置仍需重新核验接单资格；接单资格暂停后，商家仍可以关闭模拟支付或配送开关。
- 下单后若出现“上一笔提交结果待确认”，使用“确认原订单结果”恢复，或先查看“我的订单”。系统保留原餐点、备注、金额和提交标识，确认前锁定编辑；刷新或离开后返回同一标签页仍可恢复。请勿清除浏览器数据来绕过提示。
- 网络请求最多等待约 20 秒；失败后会显示重试提示。订单页有最近同步时间，旧记录不会冒充刚刚同步的状态。模拟资金和配送规则保持不变。

## 学生和商家一起演练

学生使用一个浏览器会话，商家使用另一个浏览器或手机。不要在同一个共享会话中反复切换账号观察双端同步。手机继续使用启动脚本输出的同网络 5183 地址；模拟付款不需要公网 HTTPS 域名或微信客户端。

### 模拟外卖

1. 学生在示例摊位选餐，结算选择商家配送，选择模拟交接点，填写演练用收餐姓名和电话，核对餐费、配送费与合计。无需填写真实个人信息。
2. 提交后订单进入待付款。订单付款区明确显示模拟体验，使用“模拟付款”推进；不会生成微信二维码或跳转微信。
3. 模拟付款成功后，商家依次操作“确认接单”→“做好了，准备送餐”→“模拟出发送餐”→“模拟到达交接点”。
4. 到达交接点仍不是订单完成。学生执行模拟收餐确认，或把订单中的一次性收餐码交给商家核销。
5. 双方刷新后应能看到同一状态；学生可对已完成订单评价。

### 自取与到摊付款

自取仍为提交订单 → 商家接单 → 商家出餐 → 付款 → 取餐核销。出餐后，学生可使用模拟线上付款；也可演练到摊付款，由商家确认线下收款再核销。支付结果待确认时，先查询或关闭当前模拟支付，不能同时确认另一笔线下款项。

### 测试其他情况

正常流程以外的演练入口集中在付款或退款区的次级操作中。商家拒单、退款和配送问题放在订单的“更多操作”，退款对话框提供模拟异常测试及恢复操作。改变模拟结果只影响当前登录者有权操作的这笔订单。

退款未结束或配送出现问题后，商家从工作台“查看售后”进入“售后跟进”，不用在已取消或已完成的历史订单中逐笔寻找。这里按订单计数，普通待付款不会混入。退款关闭、异常仍代表未退回；查询沿用原退款，模拟结果也必须明确操作，刷新不会替商家宣告处理完成。付款需人工核对时保留运营核对提示，不提供绕过核验的按钮。

学生进入“我的订单 → 退款与待处理”，打开详情可“刷新退款状态”或“刷新款项处理状态”，读取最新处理记录；不会因此再次付款、退款或恢复配送。订单虽已取消或完成，款项待处理时仍会自动同步；同步失败保留上次结果并显示提示。实际验证范围见[售后跟进验证](followup-verification-20260929.md)。

| 演练 | 应观察什么 |
| --- | --- |
| 付款失败 | 保留订单与明细，不当作收款成功；允许根据当前状态重新发起付款或取消 |
| 付款结果待确认 | 保留支付占用，不重复创建付款，不允许线下收款或核销；再模拟成功或失败以恢复 |
| 重复付款点击 | 使用同一笔付款记录，不能生成两笔已收款或重复扣库存 |
| 付款前取消/超时 | 已有付款记录先确认关闭；取消后库存和配送容量只释放一次 |
| 付款后、接单前取消/拒单/超时 | 终止履约，模拟退款包括配送费；原订单不因退款或迟到结果重新开始配送 |
| 制作后的取消 | 先申请，由商家处理；已经制作的食品不因为退款自动补回库存 |
| 退款处理中/异常 | 仍显示处理中或异常，不能提前显示退款成功；补充模拟结果后查询同一退款编号 |
| 配送异常 | 记录说明，解决并保存结果后才能继续；不能跳过异常直接确认送达 |
| 收餐码重复使用 | 首次有效核销后不能再完成一次 |
| 收摊、位置过期、售罄、价格或配送费变化 | 后端仍拒绝不符合条件的下单，变价需重新确认 |

退款模拟只是账面演练，不会向银行卡或微信零钱退钱。商家数据页中的模拟金额也不是可提现金额或真实营业收入；模拟日报导出的文件名及内容保留模拟标记。

订单、收付款、退款和商品销量按模式分开；浏览和接口事件仍属于同一摊位的共享访问记录，因此当前转化率仅用于流程观察，不能当作真实经营转化率。

## 开发环境准备

仅部署人员需要处理这一节，普通商家只操作网页中的服务开关。

运行环境须同时满足：`SERVICES_SIMULATION_ENABLED=true`、`DEMO_MODE=true`、`DJANGO_ENV` 不为 `production`，并且摊位是示例摊位。生产模式禁止启用模拟服务。模拟开关与真实的 `WECHAT_PAY_ENABLED` 相互独立，模拟不需要支付凭据。

开发预览统一使用启动脚本，在本项目服务未运行时执行：

```powershell
powershell -File scripts/start-dev.ps1 -Lan -Simulation
```

`-Simulation` 明确开启开发模拟运行环境，执行迁移并准备示例交接点；`-Lan` 保留同网络手机访问。脚本保留商家原来的服务开关，**重启不会重新打开商家主动关闭的支付或配送**。第一次体验时在商家页打开需要的开关。脚本拒绝在生产环境开启模拟，端口已经被占用时会提示，不会关闭其他项目。后续重新启动若仍要演练，请保留 `-Simulation`。

部署人员分步操作时可以直接注入环境、迁移并运行准备命令：

```powershell
# 项目根目录；环境变量需要传给后端和后台任务进程。
$env:SERVICES_SIMULATION_ENABLED = 'true'
$env:DEMO_MODE = 'true'
.\backend\.venv\Scripts\python.exe backend\manage.py migrate
.\backend\.venv\Scripts\python.exe backend\manage.py prepare_simulation
```

准备命令只处理示例服务与专属模拟交接点，不重置账号、订单、库存、营业状态或位置确认时间；默认不改变商家的开关选择。部署人员有意为一次演练统一开启示例服务时可另加 `--enable-services`，不要将它放进每次启动步骤。启用前仍须确认当前商家已开摊、位置有效且有库存。启停开发服务应使用本项目脚本并保留 LAN 配置，不要关闭其他项目的端口或进程。

环境变量由启动进程注入，Django 不自动读取任意 `.env`。修改环境变量后需要重启本项目后端及两个后台任务，使网页、超时任务和支付查询任务使用一致的模式；前端继续使用 5183，后端继续使用 8087。

## 模式与接口边界

订单、付款记录、退款记录分别保存 `mode: simulation | live`。模式由服务器决定，不能靠学生请求把普通订单改成模拟订单。新示例摊位订单始终保留模拟来源，即使没有开启线上模拟功能。退款沿原付款记录路由，不依赖后来修改的商家开关。

迁移会将旧示例摊位中没有任何线上支付记录的演练订单标为模拟，防止过去的到摊付款测试混入真实统计；已有线上支付记录不重新分类。不要通过后台或数据库修改历史模式来补账。

| 接口 | 模拟模式用途 |
| --- | --- |
| `GET/PATCH /api/v1/merchant/stalls/{id}/services` | 查看和修改所属摊位的线上支付与外卖开关 |
| `POST /api/v1/orders/{id}/payments/wechat`，`channel: simulation` | 为当前模拟订单建立持久付款记录，不访问微信 |
| `POST /api/v1/orders/{id}/payments/simulate` | 提交当前 `payment_id` 与 `outcome: success / failure / pending` |
| 商家原退款接口 | 模拟订单沿同一退款流程保存记录，以原付款模式处理 |
| `POST /api/v1/merchant/orders/{id}/refunds/simulate` | 提交当前 `refund_id` 与模拟退款结果 |
| `/api/v1/merchant/metrics?mode=simulation` | 只统计模式快照为模拟的订单；真实统计使用 `mode=live` |

所有模拟写接口仍需登录、CSRF 及订单/商家所有权；不能操作其他学生或商家的订单。微信通知接口只处理真实付款记录。模拟交接点有独立标志，即使误改为启用也不能用于真实配送。

若整套模拟运行环境关闭，旧模拟线上/配送订单保留其身份，不得改用真实网关付款、查询、退款或继续配送。要继续这些演练应恢复允许的开发模拟环境；不能通过改数据库模式或复制示例流水变成真实交易。原有开发示例中的纯到摊付款自取流程仍可使用，前提是这笔订单没有模拟线上支付记录；其模式仍标为模拟，不进入真实营收。生产环境不允许处理这些演练记录。

## 之后怎样接真实服务

1. 准备独立生产数据库与 HTTPS 环境，保持 `DEMO_MODE=false`、`SERVICES_SIMULATION_ENABLED=false`。不要把演练库直接作为正式营业账本。
2. 录入非示例商户、商品和获准使用的真实交接点，完成交易和配送准入核验。示例点不会自动转成真实点。
3. 按[微信支付说明](wechat-payments.md)配置每家商户自己的收款账户与密钥，先完成 Native/H5、查询、关单、退款及通知的真实小额联调。
4. 按[配送使用说明](delivery-guide.md)准备交接安排、人员、费用、时段和运力，再由商家启用真实服务。
5. 核对订单、支付、退款、库存和双方收餐操作后再放量。既有模拟记录仍是模拟记录，不能改名为真实收款或用于正式对账。

网页和订单流程可沿用，替换的是受服务器控制的服务模式与支付配置。真实接入仍需要商户资料、环境部署和实际联调，不能仅通过一个商家开关免去这些准备。
