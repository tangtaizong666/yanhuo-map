# 微信支付：接入、部署与日常处理

更新日期：2026-10-03。当前代码已提供普通直连商户的微信 Native 扫码、H5 支付、查询、关闭支付、全额原路退款和通知验签。**真实支付默认关闭，示例环境不会真实扣款；接通代码不等于商户产品权限、域名审核或真实收款已经开通。**

用户已要求先用模拟支付与配送试流程。开发环境另设带明确标识的模拟模式，操作说明见[模拟体验指南](simulation-guide.md)，实际验证见[模拟验证记录](simulation-verification.md)。下文的凭据、微信通知与真实收退款要求均针对真实模式；模拟按钮不访问微信，不需要商家填写密钥，也不能作为已开通收款的证明。

## 这一版怎样付款

学生选餐后进入结算页，支付方式随履约方式明确展示。订单列表显示付款状态，订单详情顶部展示付款区；尚未开通时显示原因。看到入口不代表当前已可扣款。

**到摊自取**：学生先提交订单，商家接单、出餐，订单到达“待取餐”（`ready`）后，学生才可以选择微信付款或到摊付款。自取准备阶段不提前收取线上款项；原有 5 分钟接单超时取消流程保持不变。

**商家配送**：学生确认交接点、联系信息和含配送费的总额后，订单进入“待付款”（`pending_payment`）。真实模式的微信付款经后端核实后才进入待接单，未付款不能备餐配送，也不能改为线下收款。真实模式未配置微信支付时不开放新配送订单；学生仍可选择自取。模拟模式通过独立的“模拟付款”操作推进，不会产生微信流水。配送取消和超时后的退款说明见下文及[配送使用说明](delivery-guide.md)。

微信支付成功由后端通过已验签的通知或主动查单确认；浏览器跳回页面、学生点击“已支付”、二维码倒计时结束，都不能改变收款状态。自取仍需核验学生出示的 8 位取餐码；配送需实际到达交接点后由学生确认收餐或由商家核验一次性收餐码，付款成功不代表已完成交付。

- **Native**：展示服务端生成的本次订单二维码，由另一台设备上的微信扫码。不会生成个人收款码。
- **H5**：商户实际开通后，在手机外部浏览器跳转微信收银台。微信内网页 JSAPI、公众号授权与 OpenID 流程尚未实现；H5 不能当作 JSAPI 使用。微信官方也要求回跳后查询真实订单结果。[H5 调起指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791835)
- 未开通某通道或配置不完整时，自取继续支持到摊付款，配送暂不开放。在线支付结果未知时，先查清或确认关闭该次支付，不能直接切换线下收款。

## 每家商户分别收款

本实现采用 `mode: "direct"`，每个独立经营主体使用自己的微信商户号。运营需要建立两处一致绑定：

1. Django 运营后台的 `MerchantProfile.wechat_pay_account` 填写服务器配置中的账户键，例如 `example_business`。
2. 对应 JSON 账户的 `merchant_profile_id` 填写该商户档案真实主键，`mchid`、`appid` 和凭据属于该商户。

配置会拒绝重复的商户档案绑定和重复收款商户号。相同经营主体下的摊位可以共用自己的商户档案；不能把不同主体强行合成一个档案来绕过校验。网页和普通商家接口不能指定收款账户、金额或凭据。

**不支持平台普通商户号替所有摊位混收后再转账，不提供平台钱包、提现、自动分账或服务商子商户模式。** 若目标商户无法获得当前产品权限，需要另行评估合法适用的服务商接入，不能借用其他商户号凑齐配置。交易准入和经营地点核验仍独立有效，详见 [配送与真实运营评估](delivery-assessment.md)。

商户需要自行完成微信侧入驻、产品权限及 AppID 绑定。H5 还要求支付域名配置和相关审核；当前官方接入准备列出的主体、AppID 类型和材料并非对所有流动摊贩自动适用。以商户平台实际审核结果为准。共享校园网站域名涉及多商户时，应先逐户确认域名主体及授权条件，不能仅在 JSON 写上 `h5` 就认为已开通。[H5 开发接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015614193)、[H5 域名配置](https://pay.wechatpay.cn/doc/v3/merchant/4013287193)

## 服务器配置

环境变量的实际名称如下。使用 Docker 时由 Compose 注入；非 Docker 启动需由进程环境注入，Django 不会自行读取 `.env`。

| 名称 | 默认/含义 |
| --- | --- |
| `WECHAT_PAY_ENABLED` | `false`；总开关，控制新支付创建 |
| `WECHAT_PAY_CONFIG_FILE` | 空；必须为服务器上账户 JSON 的绝对本地路径 |
| `WECHAT_PAY_PUBLIC_ORIGIN` | 公网 HTTPS 源站，例如 `https://campus.example.com`；无路径、查询参数、账号信息，仅标准 443 端口 |
| `WECHAT_PAY_TRUST_PROXY_CLIENT_IP` | `false`；只有自控代理覆盖客户端 IP 请求头时才可开启，见下一节 |
| `WECHAT_PAY_SECRETS_DIR` | 仅供 Compose 支付覆盖文件使用；服务器上已存在、仓库以外的绝对目录 |

此外，`DEMO_MODE` 必须为 `false`，商户已通过交易准入且账户 JSON 的 `enabled` 为布尔值 `true`，新支付才会开放。只改其中一个开关不会绕过其他条件。

将 [假值示例配置](../deploy/wechat-accounts.example.json) 复制到服务器仓库以外的目录，命名为 `wechat-accounts.json`。示例中的主键、商户号、AppID、公钥 ID、证书序列号均需替换，示例本身不能用于收款。不要把真实配置复制回 `deploy/`。

建议目录结构：

```text
/etc/yanhuo/payments/
  wechat-accounts.json
  merchant-a/
    apiclient_key.pem
    api-v3-key.txt
    wechatpay-public-key.pem
```

| JSON 字段 | 填写方式 |
| --- | --- |
| `accounts` 的键 | 1—64 位字母、数字、下划线或连字符；与后台 `wechat_pay_account` 一致，启用后保持稳定；`simulation-` 前缀为模拟保留，真实账户不能使用该前缀 |
| `enabled` | 单一商户的新支付开关，默认 `false` |
| `merchant_profile_id` | 对应数据库商户档案 ID，正整数，不是用户 ID 或摊位 ID |
| `mode` | `direct` |
| `mchid` / `appid` | 该经营主体的收款商户号及已授权绑定的 AppID |
| `serial_no` | 商户 API 证书序列号；不是微信支付公钥 ID |
| `private_key_path` | 商户 RSA API 私钥 PEM 路径，与上述证书序列号匹配 |
| `api_v3_key_file` | 独立文本文件路径，去除两端空白后内容必须为 32 字节；不能直接把密钥写入 JSON |
| `payment_public_keys` | 微信支付公钥 ID（`PUB_KEY_ID_...`）到 PEM 公钥文件路径的映射，用于响应和通知验签 |
| `channels` | 默认 `["native"]`；H5 审核通过并完成真实联调后才添加 `"h5"` |
| `timeout` | 可选，默认 8 秒，范围 1—15 秒 |

这是微信支付公钥模式，不是自动下载平台证书模式。公钥和 ID 应从商户平台可信渠道取得，不能根据回调提供的任意地址下载或信任新公钥。[微信支付官方客户端中的密钥说明](https://github.com/wechatpay-apiv3/wechatpay-apache-httpclient)

配置文件最大 256 KB；相对密钥路径相对于配置目录解析，不允许通过 `..` 或符号链接逃出目录。可用明确的绝对本地路径，但 Docker 容器必须实际能读取该路径；不支持 UNC/网络路径。每个 PEM 文件最大 64 KB，API v3 密钥文件最大 128 字节。

目录与文件只授予部署管理员和后端运行用户必要权限。镜像中的后端以非 root 的 `app` 用户运行；设置文件属主/组或 ACL 时，应核实该镜像运行 UID/GID，确保只读可访问，不要用全员可读写权限解决问题。真实密钥不进入前端、Docker 构建上下文、Git、聊天、截图或日志；`.gitignore`、`.dockerignore` 只是额外防护。

## 代理与真实客户端 IP

默认部署拓扑是“客户端 → 本项目 Caddy → 私有 Docker 网络中的 Django”，后端没有宿主机公开端口。H5 需要真实公网客户端 IP，`payment_views.py` 默认只读取连接对端地址。

基础 Compose 的 Waitress 启动参数在这个受控私网内显式接受 `x-forwarded-proto`，使 Django 正确识别 Caddy 终止的 HTTPS，同时继续清除其他未经允许的代理头。不要给后端追加公开 `ports`，也不要把不可信容器接入同一网络；如果改变拓扑，需要重新收紧可信来源。此 HTTPS 配置与下面默认关闭的微信客户端 IP 信任开关是两件事。[Waitress 代理参数](https://docs.pylonsproject.org/projects/waitress/en/stable/arguments.html)

提供的 Caddy 配置使用以下语句**覆盖**客户端可能伪造的同名请求头：

```caddyfile
reverse_proxy backend:8000 {
    header_up X-Real-IP {remote_host}
}
```

只有确认 Caddy 直接面对客户端，且外部用户和不可信服务不能绕过 Caddy 访问后端时，才将 `WECHAT_PAY_TRUST_PROXY_CLIENT_IP=true`。这是本项目自控部署的前提，不是让任意 `X-Real-IP` 或 `X-Forwarded-For` 变可信的通用开关。Caddy 官方文档说明 `header_up` 可覆盖请求头，`{remote_host}` 指直接连接方地址。[Caddy 请求头文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers)、[Caddy 占位符文档](https://caddyserver.com/docs/caddyfile/concepts#placeholders)

若 Caddy 前面还有 CDN、负载均衡或另一层反向代理，这个配置拿到的是上一跳地址；不要直接开启 H5，也不要直接改成读取用户提供的头。需要另行配置严格可信代理范围、入口访问限制和来源地址解析，并验证无法伪造后再上线。[Caddy 可信代理说明](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults)

## 使用可选 Compose 覆盖文件

不接支付时继续使用基础 `compose.yaml`，它不要求密钥目录存在，线上付款保持关闭。基础栈包含三个独立后台任务：`worker` 负责未接单超时，`payment_worker` 负责在途支付和退款查询，`notification_worker` 处理已验签并持久保存的通知。应用、回调进程和三个 worker 都在 `release` 成功完成迁移、静态收集后启动；已有部署升级须先按[发布流程](deployment-release.md)停写。

确需真实接入时：

1. 在服务器外部目录准备上面的账户文件和密钥；确认生产商户绑定、文件可读和公网 HTTPS 域名。
2. 在不提交到仓库的 `.env.production` 中设置 `WECHAT_PAY_SECRETS_DIR=/etc/yanhuo/payments`。`PUBLIC_DOMAIN` 填实际域名；覆盖文件会把配置只读挂载到 `/run/yanhuo-wechat/wechat-accounts.json`，并从 `PUBLIC_DOMAIN` 生成公开 HTTPS 源站。
3. 完成自控代理核验后按需要开启客户端 IP 信任。先保持总开关及商户账户 `enabled` 关闭，检查配置；正式小额验证前再只开启准备好的商户。
4. 后续所有该栈的启动、更新、查看配置与停止命令都带上相同的两份 Compose 文件。

以下是部署人员在目标服务器执行的命令示例；它们不代表本次开发已经执行了真实上线或扣款：

```bash
# 校验 Compose 结构，不输出展开后的环境值。
docker compose --env-file .env.production -f compose.yaml -f compose.payments.yaml config --quiet

# 目标服务器上完成接入准备后才执行。
docker compose --env-file .env.production -f compose.yaml -f compose.payments.yaml up -d --build

# 观察应用、回调和三个后台任务；不要开启包含密钥或解密正文的调试日志。
docker compose --env-file .env.production -f compose.yaml -f compose.payments.yaml logs --tail=100 backend callback worker payment_worker notification_worker
```

`compose.payments.yaml` 给 `backend`、`callback`、`payment_worker` 和 `notification_worker` 只读挂载外部目录；目录不存在会失败，不会自动建立空目录掩盖配置问题。图片、前端和数据库服务不读取支付密钥。普通过期任务不需要密钥。已接收通知由 worker 使用入库的验签结果处理，不再次访问微信或依赖轮换后的当前密钥；既有交易的主动查询和新通知仍需要原账户配置。

支付及退款通知地址由服务端生成，共用 `https://实际域名/api/v1/payments/wechat/notify/账户键`。该路径必须可从公网访问，不应加用户登录、重定向或浏览器挑战；只由微信通知验签校验身份。不要把本机 `127.0.0.1`、局域网 HTTP 地址或管理后台 URL 填成通知地址。API 出站固定连接 `api.mch.weixin.qq.com:443`；生产主机需要可靠的 DNS、HTTPS 出站及时间同步。

Caddy 将此路径送到独立 `callback` 服务，入口和进程都限制 2 MiB 请求体、处理并发为 2；临时容量或验签配置不可用时返回 503，通知不会误报成功。签名验证通过且通知已持久落库后才返回 204，随后由 `process_payment_notifications --loop` 异步应用业务结果。204 表示可靠接收，不表示已完成业务处理；必须监控全局 `check_operations` 中的 `notifications.dead/conflicts/overdue`，仅看进程存活不足以判断通知健康。

失败日志仅包含 `payment_notification_failed notification=<UUID> code=<安全代码>`。核对原交易、通知记录及微信后台后，可用 `python manage.py retry_payment_notification <UUID> --reason '核验后重试'` 重排队；原事件、处理次数和摘要保留。确认通知冲突已核验时加 `--acknowledge-conflict`，该操作只记录审核并清待处理冲突计数，不重排队、不修改资金事实。命令在目标栈的 `exec backend` 内执行，仍须带两份 Compose 文件；不要把任意错误文字当作已退款证据。

## 日常付款、撤销和退款

| 情况 | 系统行为与运营操作 |
| --- | --- |
| 创建中、待付款、结果待核对 | 保留支付占用，禁用手工线下收款。先查询结果；关闭网页不会关闭微信交易 |
| 自取学生改为到摊付款 | 调用关闭支付并核实终态；只有明确已关闭且未付款，才恢复到摊付款。配送关单不转换为线下付款 |
| 微信付款成功 | 记录服务端核实结果和付款时间，商家不再点击线下收款；自取继续取餐核销，配送继续真实履约及收餐确认 |
| 自取微信已付款后需退款 | 所属商家对待取餐或已完成订单发起全额原路退款，二次确认金额并填写理由；首版不提供部分退款 |
| 配送预付后未接单取消、商家拒单或超时 | 终止履约并保存全额退款请求，金额包括配送费；退款结果由原微信交易查询或通知核实 |
| 退款处理中/结果待确认 | 不显示退款成功，不核销；重复请求查询同一退款编号，不生成第二笔退款 |
| 退款成功 | 自取待取餐订单转为已取消；已完成订单保留完成记录。配送终止订单不恢复履约；未开始备餐仅释放一次库存，已制作食品不自动回补 |
| 退款关闭 | 原付款仍有效，该退款没有成功，继续禁止核销；有权限的运营重新核验 CLOSED 后明确发起新尝试，保留旧记录，不自动换号再退 |
| 退款异常 | 保留处理中与异常说明，查询并按支付服务方要求处理，不同时线下退款 |
| `payment_review_required` | 付款冲突或外部退款等异常，停止人工收款、退款、核销，交运营核对，不靠后台改“已付款”解除 |

退款说明最多 80 个 UTF-8 字节，中文建议不超过 26 字。退款受理与退款成功不同，最终结果依赖服务端查单或通知；不要承诺固定到账时间。[微信退款接口](https://pay.wechatpay.cn/doc/v3/merchant/4012791862)、[支付结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791861)

## 后台查询与人工对账

`payment_worker` 运行 `python manage.py reconcile_payments --loop --interval 30 --limit 100`。每轮优先处理待查询退款和支付，旧查询优先；`--interval` 最少 10 秒，`--limit` 为 1—1000。它不根据本地超时直接判定退款或支付结束。

用户手动查单、页面自动刷新及后台任务共享数据库查询预算：同笔支付或退款默认至少间隔 5 秒，失败按 10/20/30/60 秒退避。API 返回剩余冷却时间，客户端使用单调倒计时；冷却内不会重新访问微信。关单和退款等资金操作有各自校验，不能用刷新按钮绕过查询预算或凭本地计时判断资金终态。

运营核验外部退款也遵守该预算：已记录的退款使用自己的冷却和在途租约；未记录的退款号共用原付款的一次核验预算，付款核验至外部退款查询结束期间持续持有租约，失败按整次核验退避。只有核验为原付款的全额成功退款才新增退款记录；换退款号、重复点击和旧请求返回均不能绕过调度或覆盖新请求。

支付与退款先在短数据库事务中保存稳定编号和本次请求的临时占用，再在事务外访问微信，最后重新锁定订单应用已验证结果。支付请求占用期为 90 秒，退款为 60 秒；进程异常后可以在占用到期后查询原编号，不生成替代交易号。临时占用到期不代表微信交易已关闭。后到的旧请求不能清除新请求的占用，旧的未付或处理中响应也不能覆盖已确认的付款、退款成功或退款关闭结果。

配送首次创建付款入口要求订单剩余付款时间超过 75 秒，避免在提交支付记录后被微信有效期校验拒绝。确定尚未发出 HTTP 请求的首次本地失败可以结束本次支付记录；已存在未知请求的重试不能用同样理由解除支付占用。确认配送付款成功前，会在服务端重新读取当前营业、配送设置与交接点，暂停或不再符合条件时保存全额退款补偿。

不带 `--loop` 只运行一轮，可用于已配置环境的人工补查：

```bash
docker compose --env-file .env.production -f compose.yaml -f compose.payments.yaml exec backend python manage.py reconcile_payments --limit 100
```

此命令会访问真实微信查询接口，可能依据已验证结果更新状态；不是离线配置检查。运维应监测 `payment_reconcile_failed`、长期 `reconcile`/`review`/`abnormal`、请求失败和积压。日志中的订单 ID 可用于关联后台只读支付/退款记录，不应记录私钥、API v3 密钥、支付链接或完整通知正文。

每日由运营按每家真实收款商户分别核对微信商户平台账单、本站支付交易号、退款编号、金额、币种和成功时间。当前自动任务用于订单状态核对，**尚未自动下载和核销微信交易/资金账单**。商家“收款总额”是到摊确认与微信付款的原始总额；退款按成功日期另计，不能当成净利润、银行卡到账或平台余额。

人工异常处理应保留支付服务方查询依据和处理记录；数据库支付与退款记录为只读管理视图，不提供随意改状态的按钮。在商户平台人工退款或处理异常后，应重新核对本地结果；外部退款如果触发人工核对，必须逐单确认原付款、外部退款及履约记录，不能跳过冲突直接重新收钱。

2026-10-03 已提供受限的后台资金核验工作流：订单详情进入“核验资金与处理异常”，需要 `market.resolve_payments`；服务端使用原账户查询并验签，支持全流水核验结案、外部全额退款导入、CLOSED 新尝试及异常付款逐笔补偿。每笔付款最多一个活动退款，累计成功额不得超过该笔付款；未知/部分退款/金额或主体冲突继续限制。付款、退款模式和原编号始终保留，不因迁移自动解除异常。

支付记录后台提供 `market.export_financial_reconciliation` 控制的按商户 CSV 导出，日期范围内的收款/退款与所有历史未解决差异分别成行。仍需人工与微信账单核对，不会自动下载账单或标记银行结算。命令 `check_operations` 及 worker 健康检查报告心跳、累计失败、核款积压和最老待处理时间。权限、备份恢复和逐商户开放步骤见[试点运维指南](pilot-operations.md)。

## 停用、轮换与恢复

- **暂停售卖/支付**：把 `WECHAT_PAY_ENABLED=false` 或某账户 `enabled=false`，阻止新支付；保留原账户文件、密钥、通知路由、`payment_worker` 与 `notification_worker`。已经创建的二维码/支付链接不因总开关关闭而自动撤销，应逐单查明并按需关单。
- **稳定账户标识**：支付记录保存账户键、商户号和 AppID 快照。不能删除旧账户键、改给另一家商户或覆盖为新收款主体。更换收款主体需要单独迁移方案，旧交易的查询与退款仍使用原主体；当前配置不支持一个商户档案同时绑定两个独立收款号。
- **商户签名凭据轮换**：保持账户键、`mchid`、`appid` 不变，将新私钥和对应证书序列号一起更新；先核对微信侧启用状态，再验证既有订单的查询能力，保留必要的受控恢复资料。
- **微信验签公钥轮换**：按官方渠道取得新公钥及 ID，配置映射可同时保留旧、新公钥；当前实现使用映射第一项作为出站首选 ID。待旧响应/通知处置完毕后，再按实际有效期移除旧公钥。
- **API v3 对称密钥轮换**：当前每个账户只加载一个活动密钥，不支持多版本自动解密。与微信侧协调窗口，处理在途交易并验证主动查单；旧密钥放受控加密归档，不通过重复开单规避通知解密失败。
- **备份与恢复**：备份数据库、媒体和外部支付配置/密钥目录；密钥备份单独加密并限制访问，不能只备数据库。恢复到隔离环境时保持支付关闭、不要公开旧通知域名；先核对订单/支付/退款编号和金额，再在批准的网络环境补查在途记录。不要重新生成历史支付号或退款号。

## 正式开通前验证

本地测试通过只能证明代码和界面行为，不能证明产品审核、网络与真实结算已经通过。正式开通需要部署人员和实际商户共同完成：

1. 核对真实经营主体、交易准入、收款商户号、AppID、证书、公钥及账户绑定，确认不存在跨主体代收。
2. 验证部署无密钥进入镜像/前端，外网只能经预期 HTTPS 代理，伪造 `X-Real-IP` 不会传给 Django，H5 真实 IP 与获批域名正确。
3. 在实际商户授权的小额订单上验证 Native；有 H5 权限时另测手机外部浏览器。实际付款和退款需真实商户配置，本次开发不自动执行。
4. 验证回调成功、回调延迟时主动查单、关闭未支付交易后恢复线下、付款/关单竞争、重复通知、重复退款及异常结果占用。
5. 验证跨学生/商户权限隔离、一次性核销、退款后的状态与库存规则、两台设备同步，及账单金额核对。配送需另外验证预付后取消、拒单和接单超时退款，支付未知时的占用，以及送达/收餐与退款竞争。
6. 演练 worker 中断恢复、凭据失效、暂停新支付、数据库与密钥恢复；在途结果未知时不得出现模拟成功或重复收款入口。
