# 售后跟进验证 · 2026-09-29

本轮补齐模拟试用后的问题发现与跟进流程。履约状态和款项状态分开：订单已取消或已完成，仍可能需要继续处理退款、付款核对。本轮没有接通真实微信扣款或实际送餐，没有修改后端业务处理规则。

## 页面与操作

- 商家工作台的待办区增加“售后跟进”，各商家页面也提供跟进入口，进入 `/merchant/orders?filter=followup`。较早的退款订单照常纳入，同单多个问题只计一笔，与进行中的履约数量分开。
- 跟进范围包括退款申请待确认、处理中、结果待确认、异常或关闭，付款需人工核对或结果待确认，以及履约中的配送异常。普通待付款不计入；已终止订单中的历史配送异常文字不会单独产生待办。
- 售后列表优先展示付款人工核对、退款关闭和异常，再展示配送问题等事项。已取消、已完成等原履约状态保留，不会因查询款项恢复接单或配送。
- 商家可查询原退款、处理配送异常。付款需人工核对时只提供刷新和运营核对说明，不能用一个按钮伪造核对成功。模拟退款沿原模拟记录继续，真实与模拟身份保持区分。
- 学生“我的订单”增加“退款与待处理”筛选和数量提醒，详情提供刷新处理记录的入口。订单虽已结束，只要款项仍待处理，就继续定时同步，并在返回前台时刷新。读取订单不会新建付款或退款。
- 退款关闭明确表示尚未退回，退款异常不能称为成功；服务端付款结果待确认也不能被订单“已付款”或终态摘要遮盖。款项待处理时不展示取餐码、收餐码或确认收餐操作。
- 首次加载失败显示“尚未同步”和未知数量，不显示假零；后续读取失败保留原列表与数量，提示是上次同步结果。切换账号、摊位后不接纳旧请求的迟到结果。

浏览器用例拦截业务 API，未向当前演练数据库写入订单。后端测试显式使用独立内存 SQLite，测试结束后销毁；支付网络使用测试替身。本轮没有重新执行 PostgreSQL 并发、真实微信或实体手机验证。

## 本地体验与边界

2026-09-29 验证本机商家售后页面、后端健康接口、同网络 `http://10.53.8.40:5183/merchant/orders?filter=followup` 及配置代理均返回 HTTP 200。前端继续使用 5183、后端 8087，没有关闭其他项目或改变局域网配置；实体手机仍需连接可互访的同一网络，IP 以启动脚本输出为准。

模拟操作说明见[模拟体验指南](simulation-guide.md)。真实模式需要原接入文档中的商户、HTTPS、网关和运营准备；人工核款仍由运营核对，刷新页面本身不会解决款项异常。当前商家订单接口返回该摊位所有订单，数据量扩大后需服务端筛选与分页，不能先截断列表再计算售后数量。
