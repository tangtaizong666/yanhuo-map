# 单校园试点运维与资金核验

本指南对应 2026-10-03 安全与可靠性改造。代码支持真实微信 Native/H5 接入；部署开通、真实交易验收及实体手机测试仍是独立上线条件。首批只开放少量已核验商户和有人值守的时段，不开放真实配送。

## 验证与升级

在项目根目录执行：

```powershell
.\scripts\verify-pilot.ps1
# 全量 PostgreSQL/PostGIS 并发回归，附带隔离备份恢复演练
.\scripts\verify-pilot.ps1 -Postgres
```

脚本使用已有后端虚拟环境、前端 node_modules；PostgreSQL 模式需要 `backend/.runtime/postgresql.zip` 和 `postgis.zip`，来源与准备方法见 backend/README.md。每次展开新临时运行时和数据目录，使用随机密码，只绑定回环端口 55432，结束关闭自身数据库。浏览器用 5193 上的独立 fixture 服务；端口占用会停止提示，不终止其他项目。日志与浏览器产物写入 `.runtime/pilot-verification-时间/`。

默认检查 Django 配置、迁移一致性、全量 SQLite 回归、TypeScript、生产构建、隔离浏览器 fixture、生产存储拒绝启动以及真实 API 集成。真实 API 使用临时 SQLite/媒体与独占 8097/5195，验证自取核销及模拟付款/退款，结束回收自身进程。SQLite 跳过真实行锁测试，不能代替 `-Postgres`。`-SkipBrowser` 跳过全部浏览器阶段。脚本不启动、不迁移、不 seed 本地工作数据库，不需要微信密钥，不发起真实付款。

部署顺序：

1. 保存本次代码版本、依赖锁、镜像标识、环境变量清单与备份编号。暂停新单；已有付款和售后继续由值守人员处理。
2. 完成下述一致性备份，并在隔离环境实际恢复。数据库、媒体与支付密钥缺一不可。
3. 更新依赖与镜像。在新版本接流量前运行迁移；新增权限应按职责显式授予。旧 `is_staff` 不再隐含全部商家权限。
4. 启动后端、`expire_orders --loop` 和 `reconcile_payments --loop`；通过业务健康和两个 worker 心跳检查，再逐商户恢复新单。
5. 抽查自取、到摊收款、库存、价格变动、位置过期、退款限制及商家默认首页。运营人员留守观察核款积压。

迁移保存既有数据和原交易编号，不自动解决历史异常。退款由一对一改为多次尝试后，不可把生产库直接退回旧版 schema：旧代码无法正确处理多次退款。代码回滚优先使用兼容当前 schema 的修正版；确需整库恢复时，应先停写并保存故障时完整快照，核对备份时间之后的微信账单和回调，再由负责人执行恢复。不能因回滚丢掉实际收款或重复发起退款。

本机开发端口仍为 5183/8087；`start-dev.ps1 -Lan` 的同网络访问方式不变。本轮验证不会操作工作数据库；首次在现有开发环境启用新代码前，先备份，再正常运行 `backend/manage.py migrate`。

## 日常监测

```powershell
.\backend\.venv\Scripts\python.exe backend/manage.py check_operations
.\backend\.venv\Scripts\python.exe backend/manage.py check_operations --worker expire_orders
.\backend\.venv\Scripts\python.exe backend/manage.py check_operations --worker reconcile_payments
```

命令输出 JSON，正常退出 0；worker 缺失、超过默认 120 秒未成功或出现错误时退出非零。整体检查还报告正式支付在途数、未结案退款数、待人工核款订单数及最老待处理秒数；超过默认 600 秒或存在人工核款时为 `attention`。阈值可通过 `--max-heartbeat-age`、`--max-payment-age` 调整。没有心跳记录表示尚未观测到成功运行，不能标绿。

Compose 对两个 worker 分别配置健康检查。容器 unhealthy 是可见信号，不等于已经接通短信或值班告警；生产部署应将非零退出和 unhealthy 接入现有监控。心跳后台记录上次尝试、上次成功、上次失败、累计异常次数与错误类别，不记录远端原文或凭据。公网 `/api/v1/health` 不消耗游客限流额度。

`expire_orders --batch-size 100` 有界处理、跳过已锁订单并逐条提交；只读订单接口不再清理全站订单。下单只清理目标摊位相关到期预约。资金未明记录由核款流程处理，不能用超时释放付款限制。登录失败计数超过保留期限后由该 worker 分批清理；商品创建幂等记录长期保留。

## 运营权限与资金处理

普通商家只处理自有对象；运营账号必须同时为 active staff 并有对应权限。超级管理员独立放行，建议仅用于受控维护。

| 操作 | 跨商家运营权限 |
|---|---|
| 读取订单、报表与取餐查单 | `market.view_order` |
| 订单经营操作 | `market.change_order` |
| 新增商品 | `market.add_product` |
| 商品资料、补货、库存盘点 | `market.change_product` |
| 摊位设置、营业、图片 | `market.change_stall` |
| 经营主体联系方式 | 同时要求 `market.change_merchantprofile` |
| 发起正常订单退款 | `market.add_paymentrefund` |
| 异常资金核验及显式补偿 | `market.resolve_payments` |
| 资金清单导出 | `market.export_financial_reconciliation` |

在 Django 后台订单详情进入资金核验；在支付记录进入按商户对账导出。后台可见性还需对应对象查看权限。订单金额、付款成功、退款成功不能直接编辑。

处理顺序：

1. 核对订单、原付款、模式和金额，填写具体处理原因。每次查询使用付款记录绑定的原商户配置并验证响应签名与身份金额，保留操作人及脱敏依据。
2. 关闭或异常退款不等于已退回。若原退款已由服务端重新核验为 CLOSED，授权运营可明确发起新的全额尝试；旧编号与结果保留。处理中、异常待确认的原退款不能直接再开一笔。
3. 若商户已在微信侧全额退款，提供该商户的退款单号，由服务端查询并核对归属后导入。浏览器截图、手输“已退款”或跳转地址不能作为结案依据。
4. 对迟到付款或重复收款逐笔核验并补偿。单笔付款最多一个活动退款，成功总额不能超过该笔实收；首轮只支持全额。部分退款、未知付款、金额/主体冲突及查询超时继续留在待处理队列。
5. 全部记录核验完整后执行结案。未清理的异常不能恢复收款、出餐、配送或核销；两端正常取餐凭证也会隐藏。每次重试必须保留原操作键及内容，不能在结果未知时换键重发。

每日按商户、真实模式导出付款、退款、未解决差异，与微信商户账单逐笔比较商户订单号、微信交易号、退款号、金额、币种和成功日期。未解决差异次日继续跟进，不把“本地支付金额减退款金额”冒充银行已结算净额。CSV 含交易信息，只保存在授权位置。

## 备份与隔离恢复

试点至少每日备份，发布或迁移前额外备份；按可接受的数据损失和恢复时间制定留存规则。备份应加密、限制访问并保留校验值，不能提交到 Git、放到公网媒体目录或写到日志。

备份集合必须包括：

- PostgreSQL 自定义格式 `pg_dump --format=custom`，以及数据库版本、PostGIS 版本、角色/扩展初始化说明。
- 同一维护窗口的媒体完整目录/卷，保留商家原图及路径。暂停写入或使用存储一致性快照，避免数据库引用刚上传但未备份的照片。
- 仓库外支付配置、商户私钥、API v3 密钥及微信验签公钥，加密保存；解密凭据分开保管。保留仍有在途交易的历史 account key 和商户绑定，不能用新商户配置覆盖旧记录所需配置。
- 配置清单、代码版本、镜像标识和备份时间。生产认证密钥/支付密钥不应混进公开校验报告。

恢复演练在全新隔离库和媒体目录进行，禁用真实微信付款并隔断出站网关、公开回调与定时自动补偿：初始化相同扩展，用 `pg_restore --exit-on-error` 恢复，验证表数量/金额/外键/状态/幂等键/原付款退款编号/历史尝试关联；检查上传图片可读、模拟与真实模式不混淆。确认负责人员可以解密支付配置，但不要在恢复报告打印密钥。最后验证登录、只读订单和 worker 命令，记录恢复耗时、校验结果与差异。

一键 PostgreSQL 验证会自动演练全量表内容哈希比较、媒体字节恢复及加密的**虚拟支付配置**恢复，包含模拟付款、关闭退款、后续成功退款和核验证据。它证明恢复工具链，不证明生产备份介质、真实商户密钥或生产恢复时间已验收。

## 逐商户真实开通

开通前需：经营主体授权、正确商户号/AppID 绑定、Native/H5 产品权限、HTTPS 公开域名、可达且验签正确的通知地址、原商户配置持久保存、可信代理客户端 IP、值守及退款处理人。遵循 [微信接入说明](wechat-payments.md)。

微信内浏览器未实现 JSAPI，明确引导使用外部浏览器或到摊付款。不要把 Native/H5 的入口显示当成已开通，也不能遇到支付故障自动回退为模拟。

每个商户分别完成有授权的小额实付、主动查单、回调重放、取餐核销、全额退款、关闭退款处理及次日账单核对。Android、iPhone 上分别在 360/390 等真实设备窗口测试键盘、焦点、付款跳转返回、弱网和触控；768/1440 检查桌面与平板。浏览器模拟 viewport 不能替代实体手机验收。没有通过前保持该商户真实支付关闭。

## 请求入口约束

DRF 固定 3.17.2，Pillow 固定 12.3.0。Caddy 和 Waitress 均限制请求体 6 MiB；应用上传处理器累计文件流超过 5 MiB 提前终止，图片只以 JPEG/PNG/WebP 解析，再做像素检查、重新编码和 EXIF 清除。Caddy 配置依据 [request_body 官方文档](https://caddyserver.com/docs/caddyfile/directives/request_body)。

后台和 API 共用 PostgreSQL 原子失败计数，默认账号 10 次/IP 60 次/15 分钟；成功不计失败额度。只在后端无法被外部绕过、可信代理覆盖 X-Real-IP 的边界开启 `AUTH_TRUST_PROXY_CLIENT_IP`；不信任客户端自填 X-Forwarded-For。校园 NAT 下 IP 阈值需根据观测调整，不能为某一用户关闭所有账号的防护。
