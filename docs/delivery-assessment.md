# 烟火地图：配送范围与分阶段交付

初次评估：2026-09-26；范围更新：2026-09-27。用户已确认继续推进基础配送接入。本文说明建设范围与真实营业条件；代码接入不代表商户已经具备收款或配送能力。实际能力以[配送使用说明](delivery-guide.md)为准，验证范围见[配送验证记录](delivery-verification.md)。

**当前建设“商家自送至指定交接点”的基础功能，真实配送保持条件控制。** 学生应能清楚区分到摊自取与配送，查看可用点位、费用和服务说明；没有支付或履约配置时显示具体未开放原因，不能提交真实配送订单。用户于 2026-09-27 明确要求先提供模拟版，现以单独模式演练付款、配送及退款，见[模拟体验指南](simulation-guide.md)；模拟结果不得冒充真实微信付款或真实送餐。自取及到摊付款继续可用。

配送订单采用先付款、后接单备餐的流程。已付款订单拒单、接单超时或同意取消必须进入可追踪的退款处理；付款、配送和退款分别记录。商家发出餐点不等于学生收餐，未收餐不能自动标记完成。首版不包含独立骑手端、自动派单、实时轨迹、送寝承诺、第三方配送接口或跨摊合单。

## 先确定能在哪里送、由谁送

| 方案 | 适用条件 | 主要成本与限制 | 建议 |
| --- | --- | --- | --- |
| 线上付款＋到摊自取 | 学生愿意步行，摊位位置可信，商户允许在线交易 | 支付、退款、备餐和取餐管理 | 当前优先完成，保留到摊付款 |
| 商家自送 | 商家有独立配送人员、固定小范围，配送不影响出餐 | 人工、培训、容器、峰值运力；商家单独看摊时通常不适合兼送 | 有实际履约能力的商家可参与小范围试点 |
| 第三方配送 | 当地有服务覆盖、可签约、取送点明确 | 逐单报价、峰值加价、取消费用、接口与售后责任 | 先询价和线下验证，再决定是否接 API |
| 定时集中送至指定取餐点 | 相近起点/终点有足够订单，校方允许交接与存放 | 集货等待、交接人员、保温与取餐点管理 | 优先验证的校园试点形式，可由商家或第三方承运 |
| 平台自营即时配送 | 稳定较高订单密度和专门运营团队 | 招募、调度、劳动保障、安全培训、设备、异常处置 | 当前阶段暂缓 |

校园通行不能按地图距离推断。中北大学的现行校内配送车辆规定涉及校门取餐设施；广东工程职业技术学院的通知要求校外外卖放在指定取餐点。它们说明学校规则会直接影响交付方式，不能把其他学校的规则当成目标校园的授权。先与目标学校保卫、后勤确认可用交接点、开放时段、人员/车辆通行及存放管理，再设计配送范围。[中北大学规定](https://aqbw.nuc.edu.cn/info/1029/3887.htm)、[广东工程职业技术学院通知](https://www.gdep.edu.cn/hqc/info/1079/2112.htm)

对于本项目，固定校门交接点只有在确实减少学生步行、排队或等待时才有价值。如果摊位本来就在同一校门，额外收费送到门口可能没有足够收益；应先访谈学生，并用实际订单验证付费意愿。

## 真实营业前的条件

现行《网络餐饮服务经营者落实食品安全主体责任监督管理规定》自 2026-06-01 施行，原办法同时废止。第 22 条涉及实体经营门店、有效经营资质及实际地址一致；第 15 条要求订单自交易完成起保存不少于三年；第 27—30 条涉及封口包装、配送培训、受托方审核和配送食品安全。流动摊位的具体交易资格需逐户核实，不能以地图展示、演示环境的“已核验”或支付开户替代准入。[市场监管总局现行规定](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2026/art_d04d512f5ad8470eb61a652c0061dc3a.html)

这些要求在产品中的具体落实建议：

- 只给核验通过、经营地点和取货点可确认的商家开放配送；保留位置过期停单。商家移动位置后，未履约订单不能静默改地址，应联系用户和承运方处理。
- 与承运方写明收餐检查、封签异常、丢损洒漏、无法联系、超时、天气停运及投诉责任，准备人工值守联系人。
- 实测每种菜品的可配送范围和包装效果；不适合等待或运输的商品仅开放自取。时段容量由出餐和运力共同决定。
- 若使用学生兼职，也需要明确报酬、人员管理、交通安全及相应保障；不要把“校园互助”当成免除运营责任的方案。平台配送人员权益与安全安排应结合实际合作关系落实。[七部门关于外卖送餐员权益的指导意见](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_358bb682f79a497a95a245531b7abac0.html)

## 先算一单能否覆盖成本

以下是**平台视角的假设算例**，并非支付或配送服务商报价，也不是项目已经实现的经营数据。食品销售额属于商家，不能全部算成平台收入。

```text
每单贡献 = 用户配送费 + 商家给平台的服务费
         − 承运成本 − 平台承担的支付费用
         − 平均客服成本 − 平均赔付损耗 − 平台补贴

每时段经营结果 = 完成订单数 × 每单贡献 − 该时段固定运营成本
集中配送每单承运成本 = 每趟总成本 ÷ 该趟实际成功交付单数
```

假设餐费 20 元、用户配送费 3 元、商家服务费为餐费的 5%（即 1 元）；支付费率暂按 0.6% 测算，计费金额 23 元；每单客服摊销 0.30 元、赔付损耗摊销 0.20 元、补贴为 0。

| 假设履约方式 | 每单承运成本 | 每单贡献，四舍五入到分 |
| --- | ---: | ---: |
| 逐单配送，每单 5 元 | 5.00 元 | −1.64 元 |
| 集中配送，每趟 12 元，成功交付 4 单 | 3.00 元 | 0.36 元 |
| 集中配送，每趟 12 元，成功交付 6 单 | 2.00 元 | 1.36 元 |

这些数值尚未扣除固定人员、取餐点、系统维护及税费等成本；集中配送有正贡献也不等于盈利。若每趟成本 12 元，在上述其他假设不变时，至少需要 `ceil(12 ÷ (3 + 1 − 0.138 − 0.30 − 0.20)) = 4` 个成功交付订单，才能覆盖所列变动成本。失败、退款和空跑仍会增加成本，不能只用接单数计算。

实际试点前，用承运方报价、支付合同费率、退款费用规则和现场工时替换上述假设。额外包装由谁承担也要计入对应主体成本；同时检查商家扣除服务费和包装后的利润，不能只使平台账面为正。

## 配送上线时必须一起完成的功能

下表用于真实运营的完整性检查，包含第三方配送等后续能力，并非本轮全部已经实现。首版采用商家自送、固定交接点和人工节点确认；外部配送事件、实时轨迹、独立承运权限等仅在接入相应服务后建设。当前已实现字段和流程见使用说明。

| 环节 | 最小可用能力 |
| --- | --- |
| 服务范围 | 商家分别配置支持方式、区域/指定点、时段、容量、停运状态；服务端再次校验，不能只禁用前端按钮 |
| 下单报价 | 保存餐费、包装费、配送费、支付总额、交付方式、地址/取餐点、预计送达区间的快照；报价过期重新确认 |
| 支付与售后 | 付款、履约、退款分别记账；回调验签、重复通知幂等、退款结果查询、对账、人工异常处理；支付成功不能直接标记送达 |
| 商家交接 | 真实出餐后发起交接，保存承运主体、交接人和时间；商家交餐给承运方不能算学生收餐 |
| 配送执行 | 待分配、已接单、已取餐、配送中、已送达、异常等独立配送状态；第三方事件校验并处理重试、乱序和重复事件 |
| 交付证明 | 学生确认或一次性送达码，记录实际交付时间；放至取餐柜时先显示“已放至指定取餐点”，不冒充本人签收；异常有人工核查 |
| 时间与位置 | 无轨迹服务时仅展示真实节点及更新时间；不生成假骑手图标、虚构位置或精确倒计时；延误需更新说明 |
| 地址与权限 | 仅向履约所需人员显示必要地址和联系方式；其他商家、其他配送员不可访问，后台访问可审计 |

沿用一单一个摊位。初期集中配送也不要把多摊餐费合并成一笔订单，以免扩大退款、结算和迟到归责复杂度。商家交接码与用户收餐确认应分开，不能让同一个已暴露的取餐码同时证明两次交接。

订单取消、退款和履约异常的建议规则如下；正式上线前应在结算页和服务规则中清楚展示，并结合真实服务协议确定费用归属：

- 商家拒单、缺货或系统无法安排履约时，进入可追踪的退款流程，未提供的服务费用一并处理。退款只在支付服务端确认成功后显示到账完成。
- 用户取消时依据真实备餐和配送进度展示处理结果及费用明细。接单后不能简单承诺“一律可退”或“一律不退”。
- 已取餐后出现洒漏、丢件、错送、封签异常、长时间延误时，保留申诉和人工处理入口；原订单、履约记录、退款流水相互关联。
- 支付已成功但订单超时、重复回调、取消与付款同时发生，都要进入确定的补偿流程；不能让已取消订单悄悄恢复或重复退款。

地址和手机号只为履约收集，指定点配送通常不需要宿舍房间号、学号或学生证。界面应告知用途及保存安排；区分履约人员可见期限与法定归档期限，归档数据限制访问，不等于长期向配送员开放。法律要求个人信息处理有明确目的并控制在必要范围内，具体措施应随实际数据处理方式落实。[《个人信息保护法》](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_f374e8245320413181742e6d1baf4366.html)

## 何时值得试点

建议先收集连续两周真实自取经营数据及学生访谈；这只是本项目建议的观察窗口，不是行业统一门槛。系统可以先接入，满足以下条件再开放真实配送试点：

1. 学生有明确的付费配送需求，且交接点确实比自行到摊便利。
2. 校方交接安排明确；商家准入、承运人员/主体、食品包装与责任分工已落实。
3. 自取线上付款、取消、退款、查单、对账和人工售后已经在真实支付环境验证。
4. 同一时段和路线有足够订单覆盖报价成本，保守算例下仍可接受；天气、空跑和售后费用已计入。
5. 有人负责营业期间调度与异常，不依赖网页常驻提醒代替履约值守。

首轮可以限制为一个校园、一个获准交接点、2—3 家合格商家和一个晚餐时段。日容量由实测出餐与运力设定，逐步放量；不在尚未验证时承诺全校、全天、送寝或固定分钟必达。

试点记录实际取餐/送达时间、承诺区间内交付率、失败/退款原因、每单贡献、用户复购和商家出餐延误；发生食品安全或通行问题时暂停对应服务，订单不能自动完成。把数据与同期自取订单比较，再决定扩大配送、保留定时送点，或继续只做自取。

本轮实现范围、默认关闭项和配置步骤随代码核对后记录在使用说明中。真实微信收款、目标校园授权、商家运力和费用是否可持续仍需现场联调与试点验证；自动化测试不能代替这些条件。
