# 手机操作简化与整条流程复查

本轮依据用户的实际使用反馈，重新检查学生选餐到取餐、商家接单到交餐。目标是普通商家不需要阅读大段说明就能完成日常操作；原有资金、库存、权限、位置过期和独立收款／核销规则继续保留。

## 已调整的实际体验

- 商家默认首页直接使用接单台，不再先展示统计首页。底部只有接单、菜品、更多；首页和原订单地址共用同一个处理组件。
- 接单台分为新订单、制作中、待取餐。每张卡突出餐点、份数与顾客要求，只保留当前一步的主按钮；延期、拒单、退款等在详情中操作。
- 取消申请、资金或配送问题、原操作结果待确认，保留跨分类的显眼入口。支付结果不明时不能手工确认收款；确认收款与取餐码核销仍是两步。
- 经营数据、历史订单、顾客评价、分享、账号安全和开摊清单放到更多。提醒设置移出接单首屏，监听组件保持挂载，避免切页面后悄悄关闭已开启的提醒。
- 菜品页删掉重复标题与长说明，收起补货说明；首屏展示菜品和余量。店铺页合并重复的营业／位置确认区域；隐藏摊位不再出现不可用的公开预览入口。
- 学生首页餐点图片固定比例，店铺卡片改为图片与摘要、整行餐点链接和状态。菜品详情减少装饰文字与超大图片；订单页合并重复提示，待取餐优先展示取餐码、金额和地址。
- 连续接单、出餐和收款的成功提示只保留最新一条，避免多条提示堆在手机顶部遮挡下一步；错误和其他需处理的信息不被成功提示吞掉。

## 修复的状态问题

原先只有整摊餐袋完全未变才在下单成功后清空。等待回复或恢复下单期间若又加餐，已提交部分也留在餐袋里，继续提示结算。现在给本地每份草稿一个稳定标识，提交成功只移除原请求包含的份数，保留新增、编辑过的份数及其他摊位餐袋；这些标识不发送到订单 API。

结果未知时，餐袋提供“确认下单结果”入口，不能同时走普通新结算。原请求键、金额、逐份要求保持不变。成功页餐袋为空时不再显示餐袋入口。账号变化或旧响应晚到不能清除新账号的草稿。

复查还发现浏览器允许读取、却因空间不足拒绝写入时，旧存储可能被误认为另一标签页的新数据，从而覆盖当前内存草稿。现在单独记录已观察到的存储内容；写入失败不把旧值当成外部更新。之后突然拒绝读取或写入时，账号切换仍保留各自内存中的草稿；恢复读取后也不能用旧值覆盖新增餐点。两条故障路径均有专项单元测试，其中读取拒绝用例先复现失败、修复后通过。

- 对 360／390／768／1440 宽度检查布局；手机主操作必须高于真实底栏，且用 `elementFromPoint` 检查没有被其他元素遮挡。仅“没有横向溢出”不再算操作验收通过。
