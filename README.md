## 前端设计要求

2026-09-29 日常使用优化已接入：商家工作台根据当前状态提示下一步；同一道菜可逐份选免费口味、写备注；商家接单及制作中可给出预计出餐时间和延迟说明。首页没有正在出摊的摊位时，会区分收摊、位置待确认和未收录。新增账号恢复码和可选会话系统提醒，后者不保证手机后台送达。详见[日常使用指南](docs/daily-use-guide.md)、[本轮验证记录](docs/daily-verification-20260929.md)与[真机检查表](docs/launch-device-checklist.md)。

长期视觉、素材来源与交互要求记录在 [DESIGN.md](DESIGN.md)，后续修改必须同时满足功能与美观要求。用户指定 Dribbble、Pinterest、GSAP Showcase、Recent 为持续参考来源。餐点详情使用独立地址 `/stalls/:id/products/:productId`，可从菜单、首页餐点和搜索结果进入。

学生页右上角的餐袋进入 `/cart`，按账号和摊位保存所选餐点并分别结算；访客餐袋需要明确确认才合并进登录账号，旧版共享草稿不自动归属任何账号。草稿只保存在当前浏览器，存储不可用时改用当前页面内存；库存与价格会重新核对，价格变化需要逐项确认。移除餐点或清空某家餐袋后可立即撤销。

已完成、已取消、商家拒单的订单可“再来一单”：先展示当前价格和可售数量，跳过售罄或下架餐点，确认后合并进餐袋，仍需在结算页提交订单。首页、搜索、地图、我的和餐袋会每 15 秒同步进行中订单，优先提示待取餐；关闭页面不会收到推送，网络失败时会明确提示。

## 商家工作台

商家端沿用暖橙与奶油色，在电脑上使用独立侧栏，在手机上保留“出摊／接单、菜品、更多”三个底部入口。直接访问 `/merchant`，用上面的商家体验账号登录。示例商户演练交易，不代表真实流动摊位已获交易准入。

| 页面 | 路径 | 操作 |
|---|---|---|
| 入驻申请 | `/merchant/apply` | 普通账号自助保存、提交与补充；核对团队代录申请 |
| 经营首页 | `/merchant` | 找摊商户维护位置和营业；交易商户处理接单、出餐和交餐，已有订单持续保留 |
| 订单处理 | `/merchant/orders` | 出餐台／全部订单、逐份要求、取餐码查单、取消申请、收款及核销 |
| 商品管理 | `/merchant/products` | 找摊商户维护今日供应三态；交易商户增量补货、暂停／恢复供应及盘点更正 |
| 经营数据 | `/merchant/analytics` | 1/7/30 天趋势、人气商品、回头客、来源动作、收款流水与 CSV 日报导出 |
| 顾客评价 | `/merchant/reviews` | 评分分布、待回复筛选、公开回复和撤回回复 |
| 店铺设置 | `/merchant/store` | 营业与位置确认、线上支付/配送开关、交接点与费用；店铺资料及低频配送设置集中收起 |

首页快捷入口和手机店铺页底部可进入评价管理。商家回复同时展示在学生端摊位评价与订单详情中。一个账号管理多个摊位时，可以通过顶部的摊位选择器切换。

所有商家页面都有待接单和取消申请提醒，显示最早一单的真实剩余时间；每 10 秒同步，回到页面立即刷新。点击“开启声音提醒”后会试音，新订单到达时发出短提示音，仅在当前页面打开且处于前台时有效，不是手机后台推送。

“售后跟进”与履约中的待办分开计数，同一订单有多个问题只计一笔。工作台“查看售后”或各页“跟进售后”进入 `/merchant/orders?filter=followup`，可以查询原退款或处理配送异常；付款需人工核对时只展示真实状态与刷新入口，不能手动点击伪造核对成功。

收款按 `paid_at` 计算，按北京时间自然日统计；线上、线下和退款分别列示。模拟与真实模式按订单快照分开统计，模拟金额不是实际营收。总收款包含后续退款订单，退款按完成日期另计，不能将其当作净收入或可提现余额。订单创建时间和实际完成时间分别记录；页面不提供平台钱包、提现或优惠券。

照片支持 JPG/PNG/WebP，单张最大 5 MB、2000 万像素。后端重新编码并清除 EXIF，文件保存在 `backend/media/`；生产环境使用独立 `backend_media` 持久卷，备份需同时包含数据库与媒体文件。开发上传内容不打包进生产镜像。

## 启动开发环境

需要 Python 3.11+、Node.js 22.12+。Windows PowerShell 在项目目录执行：

```powershell
.\scripts\start-dev.ps1
```

当前阶段体验模拟微信付款和外卖时，使用 `powershell -File scripts/start-dev.ps1 -Lan -Simulation`。`-Simulation` 只在非生产环境启用演练并准备示例交接点，`-Lan` 同时允许同网络手机访问；商家服务开关由网页管理，重启保留原选择。不带模拟参数时不会自动开放模拟付款。完整说明见[模拟体验指南](docs/simulation-guide.md)。

脚本首次创建依赖和本地数据库，并且只在数据库不存在时导入示例；后台进程日志和 PID 保存在 `.runtime/`。端口被其他应用占用时会停止提示，不会关闭其他项目。

后台前端由 `scripts/start_frontend.py` 创建独立进程组、断开终端输入，再运行 `frontend/scripts/serve-dev.mjs` 的 Vite API 入口；手动 `npm run dev` 仍用于前台开发。日志保存在 `.runtime/frontend.log`，前端异常及退出码记录在 `.runtime/frontend.error.log`。

停止**该脚本创建**的进程：

```powershell
.\scripts\stop-dev.ps1
```

也可以分别开启五个终端运行（均使用相同的开发环境配置）：

```powershell
# 终端 1，项目根目录
.\backend\.venv\Scripts\python.exe backend\manage.py runserver 127.0.0.1:8087
# 终端 2，项目根目录
.\backend\.venv\Scripts\python.exe backend\manage.py expire_orders --loop
# 终端 3，项目根目录
.\backend\.venv\Scripts\python.exe backend\manage.py reconcile_payments --loop
# 终端 4，项目根目录
.\backend\.venv\Scripts\python.exe backend\manage.py process_payment_notifications --loop
# 终端 5
cd frontend
npm run dev
```

首次手动安装：`python -m venv backend/.venv`，使用其中的 Python 安装 `backend/requirements.txt`，再运行 `backend/manage.py migrate` 与 `backend/manage.py seed_demo`；前端执行 `npm ci`。

默认预览在本机运行。手机真机访问需在受信任网络配置允许的主机与 CSRF 来源；高德定位还需要 HTTPS，不能把普通局域网 HTTP 的定位失败当作业务错误。

同一 Wi-Fi 下使用手机体验时，在项目目录执行：

```powershell
.\scripts\stop-dev.ps1
.\scripts\start-dev.ps1 -Lan
```

脚本自动选择物理 Wi-Fi / 网卡的私有地址，输出学生端和商家端链接，并配置 Django 主机与 CSRF 白名单；数据库和后端 8087 端口仍只在本机监听。多张网卡时可指定 `-LanAddress 你的电脑局域网IP`。手机需与电脑连接同一可互访网络，电脑保持开机；若更换 Wi-Fi 后 IP 改变，重新运行命令获取新链接。部分校园网络隔离客户端，同一 Wi-Fi 名称也可能无法互访，可改用电脑或手机热点。

局域网 HTTP 可以浏览、登录和体验自取订单；启用 `-Simulation` 后还可演练模拟支付与外卖。浏览器地理定位需要 HTTPS 与有效高德配置，未配置时仍可手动选择校园。默认 `start-dev.ps1` 不带 `-Lan` 会恢复为仅本机访问。

## 线上支付接入

自取订单在商家出餐、进入“待取餐”后才开放微信付款，同时保留到摊付款。线上结果未知时禁止手工收款，只有确认关闭未付款的微信交易后才能恢复线下付款；支付成功仍要核验 8 位取餐码。退款由所属商家二次确认，处理中的退款不会显示成功。

配送订单在结算后先进入待付款，微信确认预付成功后才交给商家接单；不提供货到付款。未接单取消、拒单和接单超时会保存全额退款请求；支付和退款未知时继续查询，不能用本地超时伪造成功。实际到达交接点后由学生确认收餐或商家核销一次性收餐码，不自动完成。

每个独立经营主体绑定自己的普通直连微信商户号，不使用平台商户号替多家摊位混收。默认 Native；H5 需要商户产品权限、AppID 绑定、获批域名和可信客户端 IP，尚未实现微信内 JSAPI。所有示例配置使用假值，代码接入不表示真实收款已经开通。

详细配置、可选只读密钥挂载、回调、轮换、对账与上线验证见 [微信支付接入说明](docs/wechat-payments.md)。不开通时保持 `WECHAT_PAY_ENABLED=false`，基础 Compose 无需密钥目录；开通时使用 `compose.yaml` 加 `compose.payments.yaml`，真实密钥保存在仓库以外。

## 配置学校、商户和地图

通过运营后台维护校园区域、商户、摊位位置、商品和经营资质公示。正式商户必须经过核验后再开启“允许在线接单”；移动取餐地点会关闭交易权限，需重新核验。管理参数可调整默认 60 分钟位置有效期和 5 分钟接单时限。

入驻审核通过只建立隐藏且未核验的商户/摊位，不自动开放交易、支付或配送；公开展示和经营准入仍分别核验。`PUBLIC_BASE_URL` 可设置分享与二维码的公开根域名。留空使用当前访问地址，并标明仅当前电脑或仅同网络体验，不把局域网二维码当成公网链接。

高德需要 **Web 端 JS API Key** 与安全密钥两个配置：`AMAP_KEY`、`AMAP_SECURITY_CODE`。前者供地图加载，后者只留在服务端。后端提供限定上游的 `/_AMapService` 代理；前端不暴露安全密钥。无配置时列表、搜索与文字地址仍可使用。坐标统一为高德 GCJ-02，不能直接录入未转换的浏览器 WGS84 坐标。

环境变量说明见 [backend/.env.example](backend/.env.example)，接口与业务实现见 [backend/README.md](backend/README.md)。环境变量由启动进程或 Docker 注入，Django 不会隐式加载任意 `.env`。

## 正式环境部署

提供 `compose.yaml`、`deploy/Dockerfile` 与 Caddy HTTPS 配置。正式部署需准备指向服务器的域名，运营主体及商户资料，以及数据库口令和随机 Django 密钥。

1. 在安装 Docker Compose 的 Linux 服务器上，将 `.env.production.example` 复制为 `.env.production` 并填入自己的值。
2. 执行 `docker compose --env-file .env.production up -d --build`。
3. 执行 `docker compose --env-file .env.production exec backend python manage.py createsuperuser` 创建自己的运营账号。
4. 在管理后台录入**非示例**校园、商户和商品。运营人员完成准入审核后才开启点单。
5. 核实 HTTPS、地图、日志、备份恢复、接单超时任务和真实双设备操作，再邀请首批学生。

生产配置默认关闭示例模式和线上支付、不建立示例账号，不公开数据库、后端或回调端口。独立 `release` 容器先完成迁移与静态收集，成功后应用及三个 worker 才启动。Caddy 将付款回调送到受限 `callback`，验签入队后由 `notification_worker` 处理；过期任务由 `worker` 执行，在途支付/退款查询由 `payment_worker` 执行。开发数据不会自动迁移进生产。开通付款后，即使暂停新支付，也应保留密钥挂载与付款查询任务处理既有交易。升级停写、发布门控、CSP 报告阶段和逐商户真实验收见[发布与48小时观察](docs/deployment-release.md)。

临时数据库备份示例（只包含数据库，不能替代完整灾备；服务器 Bash，保存在仅管理员可访问的目录）：

```bash
mkdir -p backups
umask 077
docker compose --env-file .env.production exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "backups/yanhuo-$(date +%Y%m%d-%H%M%S).dump"
```

完整备份工具见[加密异机备份与隔离恢复](docs/backup-recovery.md)：默认每30分钟调度，目标 RPO 1小时/RTO 2小时，统一保存数据库、媒体、运行配置与支付密钥，校验加密回传并提供断网 PostGIS 恢复演练。真实目的地和告警未配置时拒绝运行，不把本机卷或虚拟演练标为生产灾备成功。未经演练不要覆盖运行中的数据库；恢复后保持新支付关闭，核对支付/退款流水再补查在途交易。API/回调/操作事件可通过相应 Compose 配置的 `logs backend callback worker payment_worker notification_worker` 查看，支付栈需始终带上 `-f compose.yaml -f compose.payments.yaml`。

## 运行验收与巡检

Linux、WSL 和 CI 共用 `scripts/verify_runtime.py`，Windows 可运行 `scripts/verify-runtime.ps1 -FullRegression`。入口使用临时 Compose 项目验证 HTTPS、迁移失败阻断、工作进程恢复、PostgreSQL 库存争抢、真实加密回调，以及 SFTP/restic/PostGIS 备份恢复；不会操作开发数据库和 5183／8087。运行方法见[隔离验收入口](docs/runtime-acceptance.md)，结果见[统一证据索引](docs/runtime-evidence-20261003.md)。

生产主机的[全局巡检](docs/operations-monitor.md)每 60 秒检查业务积压、工作进程、容器与备份，持久保存通知去重和失败重试。真实异机目的地、告警接收人、商户实付及实体手机仍需单独验收。

后续[试点边界复核](docs/pilot-boundaries-20261003.md)补齐跨标签账号错配拦截、运营外部退款查询预算、到期订单积压及恢复失败告警，记录首次失败与修复后的独立验收结果。
